# CardTalk

SPA для изучения английских слов: карточки с переводом и примером употребления, фильтр по темам, профиль с большой формой и валидацией, сессионная авторизация на cookie.

Проект представляет собой фронтенд без реального бэкенда — весь API эмулируется через MSW (Mock Service Worker) прямо в браузере. Это важно для понимания разделов «Защищённость данных» и «Известные ограничения»

## Стек

- React 19.3 — UI
- TypeScript 6.0 — типизация
- Vite 8.3 — сборка и dev-сервер
- Redux Toolkit + RTK Query 2.12 — стор, кэш и слой данных
- React Router 7.18 — маршрутизация
- React Hook Form 7.88 + Zod 4.6 — формы и валидация
- MSW 2.15 — мок API через Service Worker
- CSS Modules — стили, изолированные по компонентам
- ESLint 10 — статический анализ

## Запуск

Вариант 1: npm (разработка)

Требования: Node.js 20.19+ или 22.12+ (ограничение Vite 8), npm 10+.

    npm install
    npm run dev

Приложение поднимется на http://localhost:5173.

При первом запуске MSW регистрирует service worker из public/mockServiceWorker.js. Если вы обновляли версию MSW, воркер нужно перегенерировать:

    npx msw init public/ --save

Доступные скрипты:

    npm run dev       dev-сервер с моками
    npm run build     tsc -b && vite build → dist/
    npm run preview   локальный просмотр прод-сборки
    npm run lint      eslint .

Вариант 2: Docker

Требования: Docker 20.10+ с плагином Compose.

    docker compose up -d --build

Приложение будет доступно на http://localhost:8080.

Важно понимать: MSW стартует только в dev-режиме (import.meta.env.DEV в main.tsx), поэтому в Docker-контейнере моков нет. Контейнер демонстрирует продакшен-сборку и раздачу статики через nginx. Чтобы приложение в нём работало, нужен реальный бэкенд на том же origin по пути /api.

Как устроен образ

Сборка двухстадийная (Dockerfile):

1. Стадия build — node:20-alpine. Сначала копируются только package*.json и выполняется npm ci: это отдельный слой, который Docker переиспользует из кэша, пока не изменился package-lock.json. Затем копируется исходный код и выполняется npm run build → dist/.
2. Стадия рантайма — nginx:alpine. В неё переносится только готовый dist/, без node_modules и исходников. Итоговый образ содержит статику и nginx, Node.js в нём нет.

nginx.conf делает две вещи:

- try_files $uri $uri/ /index.html — SPA-фоллбэк. Без него прямой заход на /cards или перезагрузка страницы давали бы 404, потому что таких файлов на диске нет, а маршрутизация живёт на клиенте.
- gzip on с перечнем text/js/css/json типов — сжатие статики.

.dockerignore исключает node_modules, dist, .git и мусор IDE из контекста сборки: это ускоряет docker build и гарантирует, что в образ не попадут хостовые бинарники из локальных node_modules.

MSW запускается только в dev-режиме. Импорт mocks/browser сделан динамическим внутри проверки import.meta.env.DEV, поэтому обработчики и тестовые учётные данные вытряхиваются из прод-бандла tree-shaking'ом.

Демо-доступ

    Логин: admin
    Пароль: admin

## Что реализовано

### Архитектура данных

Слой данных построен на RTK Query. В приложении один createApi (store/slices/api.ts) с пустым набором эндпоинтов — конкретные ручки добавляются через injectEndpoints в отдельных файлах (auth-api, profile-api, words-api). Это даёт один кэш, один middleware и один набор тегов на всё приложение, при этом эндпоинты лежат рядом со своей предметной областью.

Политика обработки 401 различается не на уровне инстансов api, а на уровне отдельного эндпоинта — через extraOptions:

    login: builder.mutation<LoginResponse, LoginRequest>({
      query: (credentials) => ({ url: '/authorization', method: 'POST', body: credentials }),
      extraOptions: { skipReauth: true },
    }),

Это важно: неверный пароль возвращает 401, но это не повод запускать цикл refresh → logout → refresh. Ручка помечена skipReauth, и 401 от неё доходит до компонента как ошибка ввода, а не как «сессия истекла».

Очистка состояния при выходе централизована в session listener (store/index.ts). Listener подписан сразу на два события через isAnyOf: на экшен logout из user-slice и на authApi.endpoints.logout.matchFulfilled. Ни один компонент не занимается очисткой кэша вручную — эффект listener'а вызывает api.util.resetApiState(). Двойная подписка нужна, чтобы кэш чистился и когда запрос /logout не дошёл: компонент всё равно диспатчит logout().

### Оптимизация загрузки

Все страницы подключены через React.lazy — index.ts рядом с каждой страницей объявляет ленивую обёртку, а app.tsx оборачивает Routes в Suspense. В сборке это видно по отдельным чанкам: home-page, login-page, cards-page, profile-page, not-found-page грузятся по требованию, а не одним бандлом.

CSS тоже разрезан по чанкам благодаря CSS Modules, а повторяющиеся в дизайне значения (цвета, размеры текста, радиусы, тени) вынесены в глобальные переменные в global.css.

### Карточки

- GET /api/words через RTK Query, данные лежат в mocks/data/words.ts.
- Карточка переворачивается по кнопке: лицевая сторона — слово, часть речи и пример употребления, оборот — слово и перевод. Переворот сделан на CSS (transform: rotateY + backface-visibility), состояние стороны локальное.
- Список тем не захардкожен, а вычисляется из самих слов: useMemo собирает Set из всех word.topics. Добавление слова с новой темой автоматически добавляет фильтр.
- Фильтрация по выбранной теме тоже в useMemo, чтобы не пересчитывать список на каждый ререндер.
- Заголовок карточки берётся из constants/motivation-titles.ts. getRandomTitle вызывается через ленивый инициализатор useState, поэтому заголовок фиксируется на время жизни компонента и не меняется при каждом ререндере.

### Профиль

Типы полей: text, number, textarea, date, select, checkbox (множественный выбор), radio. В types/profile.ts это оформлено дискриминированным объединением ProfileField с дискриминантом type. Благодаря этому TypeScript точно знает, что у CheckboxField поле value — это string[], а у NumberField — string, и перепутать их на этапе компиляции нельзя.

Форма построена на React Hook Form с zodResolver(profileSchema) и mode: 'onBlur'. Разделение обязанностей такое:

- нативные контролы (text, number, textarea, date) подключаются через register — неконтролируемый режим, без ререндера на каждый символ;
- составные контролы (select, checkbox, radio) — через Controller, потому что они не эмитят нативный onChange и работают с массивом значений.

Начальные значения собираются из тех же PROFILE_SECTIONS, а после успешного GET /api/profile форма наполняется через reset({ ...defaultValues, ...data }) — спред нужен, чтобы отсутствующие в ответе поля не остались undefined. Reset вызывается один раз, когда данные пришли впервые: флаг initialized защищает от повторных сбросов, иначе useEffect срабатывал бы на каждый рендер и затирал ввод пользователя.

Связанность полей реализована через visibleWhen: { field, value } — поле показывается только при определённом значении другого поля. Пример: «Имя супруга» появляется, только если семейное положение — «Женат/Замужем». Логика живёт в edit-view.tsx (функция isVisible) и применяется фильтром перед рендером секции.

Параллельно работает disabledWhen: { field, value } — поле блокируется при определённом значении другого. Пример: «Девичья фамилия» блокируется при статусе «Не женат/Не замужем». Про сопутствующий флаг valueWhenDisabled см. раздел «Известные ограничения».

Сохранение — PUT /api/profile, результат показывается тост-уведомлением, после успеха происходит переход на страницу карточек.

### Числовые поля

Field для type: 'number' рендерит input как type="text" с inputMode="numeric". Это сознательный уход от нативного type="number": нативный инпут даёт ввести e, +, -, точку и в некоторых браузерах возвращает пустую строку при невалидном вводе, что ломает контролируемый компонент. inputMode при этом оставляет мобильным устройствам цифровую клавиатуру.

Значение хранится как строка — это позволяет полю быть пустым, а не «залипать» на нуле. Проверка содержимого вынесена в Zod-схему: регулярка /^\d+$/ на «только цифры» плюс refine на диапазон (возраст 18–120, дневная цель больше нуля). Каждое правило допускает пустую строку, поэтому необязательное поле не считается ошибочным, пока его не заполнили.

### UI-компоненты

- Кастомный Select отрисовывается через createPortal в document.body — так выпадающий список не обрезается overflow: hidden у контейнеров. Позиция вычисляется от триггера в useLayoutEffect (до отрисовки, без мигания), при нехватке места снизу список раскрывается вверх, а подписка на scroll в фазе захвата и на resize пересчитывает позицию при прокрутке любого родителя. Заблокированный селект не открывается ни по клику, ни при попытке снять позицию.
- Toast — уведомления об успехе и ошибке с автозакрытием через 3 секунды.
- Input и Textarea обёрнуты в forwardRef, чтобы работать с register из React Hook Form, и принимают флаг hasError для стилизации.
- Button — три варианта оформления (action, tab, big) поверх нативного button со всеми его атрибутами.
- Header / Footer / Body — каркас страницы.
- Стили изолированы через CSS Modules. Палитра, шрифты, радиусы, тени и размеры полей вынесены в CSS-переменные в global.css. Шрифты (Inter, Fraunces) лежат локально в assets/fonts и не тянутся со сторонних CDN.

## Алгоритм авторизации

Авторизация основана на access и refresh токенах, хранимых в cookie (бэк должен задавать http-only secure куки) с автоматическим обновлением по 401.

### 1. Вход

1. login-page использует React Hook Form с zodResolver(loginSchema). Схема (schemas/login-schema.ts) требует непустые логин и пароль; режим mode: 'onBlur' показывает ошибку при уходе с поля, а не на каждый символ.
2. Сабмит вызывает мутацию useLoginMutation → POST /api/authorization с телом { login, password }.
3. Обработчик в mocks/handlers.ts сравнивает пару с ADMIN_LOGIN / ADMIN_PASSWORD из mocks/data/auth.ts. Совпало — 200 { name: 'Admin' } и установка cookie access_token=access; path=/. Не совпало — 401 { message: 'Invalid credentials' }.
4. При успехе клиент делает dispatch(setUser(response.name)) и navigate(ROUTES.CARDS).
5. При ошибке .unwrap() бросает исключение, и в catch вызывается setError('password', ...) — под формой появляется «Неверный логин или пароль». Ответ сервера намеренно не различает «нет такого логина» и «неверный пароль», чтобы не давать подсказку для перебора учётных записей.

### 2. Транспорт запросов

store/slices/base-query.ts:

    export const baseQuery = fetchBaseQuery({
      baseUrl: '/api',
      credentials: 'include',
    });

credentials: 'include' заставляет браузер прикладывать cookie к каждому запросу автоматически. Токен нигде не хранится в JS-коде и не подставляется руками в заголовок Authorization — приложение вообще не оперирует значением токена, им управляет браузер.

### 3. Восстановление сессии после перезагрузки

Состояние Redux при перезагрузке теряется, а cookie — нет. Чтобы пользователь не выпадал в гостевой режим при F5, app.tsx вызывает useGetMeQuery() при монтировании AppContent. Пока запрос в полёте, приложение показывает «Загрузка…» — так защищённые страницы не успевают отрендериться раньше времени и не редиректят авторизованного пользователя на главную. Ручка /me помечена skipReauth, поэтому 401 от неё не запускает refresh-цикл: если пользователь гость, он просто остаётся гостем.

Защищённые запросы (useGetWordsQuery, useGetProfileQuery) идут с skip: !login — пока сессия не восстановлена, они не дёргаются.

### 4. Автообновление токена при 401

Обёртка baseQueryWithReauth, через которую проходят все запросы:

    запрос → 401? — нет → ответ
              │
             да (и нет skipReauth)
              ▼
       POST /api/refresh
              │
       ┌──────┴──────┐
    успех          провал
       │              │
  повтор запроса   dispatch(logout())

Ключевая деталь — дедупликация refresh-запросов. Если страница одновременно запрашивает /words и /profile и оба получают 401, наивная реализация отправила бы два параллельных /refresh. Здесь промис обновления хранится в переменной модуля refreshRequest:

    if (refreshRequest) return refreshRequest;

Первый упавший запрос инициирует обновление, остальные получают тот же самый промис и ждут его. После завершения .finally() обнуляет переменную, чтобы следующий цикл 401 мог запустить новый refresh. Это классический паттерн single-flight.

Сам запрос /refresh идёт через голый baseQuery, а не через обёртку, поэтому его собственный 401 не запускает рекурсию.

Если refresh прошёл — исходный запрос повторяется прозрачно для вызвавшего компонента. Если не прошёл — диспатчится logout(), и приложение переходит в неавторизованное состояние.

### 5. Выход

Мутация logout → POST /api/logout (с skipReauth, чтобы выход не пытался чинить сессию, которую и так закрывают). Обработчик удаляет cookie, выставляя max-age=0. Дальше Header диспатчит logout() из user-slice, session listener в store/index.ts ловит экшен и сбрасывает кэш RTK Query. Пользователь редиректится на главную. Ошибка сетевого запроса не блокирует выход: dispatch и навигация стоят в блоке finally.

### 6. Ограничение доступа к страницам

Проверка сделана на уровне страниц: cards-page и profile-page читают имя пользователя из стора и при пустом значении возвращают Navigate to ROUTES.HOME. HomePage и LoginPage, наоборот, редиректят авторизованного на /cards. Клиентская проверка отвечает только за UX — реальный контроль доступа выполняют обработчики, каждый из которых самостоятельно проверяет сессию и отдаёт 401.

## Защищённость данных

Здесь нужно чётко разделить два уровня: какая схема заложена в архитектуру клиента и что реально защищено в текущей сборке.

### Что сделано правильно с точки зрения схемы

Клиент написан под корректную серверную модель безопасности:

1. Токен не хранится в localStorage и не проходит через JS. Это главное архитектурное решение. Токен в localStorage читается любым исполнившимся на странице скриптом — то есть одна XSS-уязвимость или одна скомпрометированная npm-зависимость означает угон сессии. Здесь сессия передаётся через cookie, которую браузер прикладывает сам (credentials: 'include'), и код приложения значение токена не видит и не трогает.
2. Авторизация проверяется на стороне «сервера». Каждый защищённый обработчик (/profile, /words) самостоятельно проверяет сессию и отдаёт 401. Клиентские проверки и редиректы отвечают только за то, чтобы не показывать пустые экраны, но не являются механизмом контроля доступа.
3. Централизованная обработка 401. Ни один компонент не работает с сессией сам — вся логика в одном baseQueryWithReauth.
4. Публичные и защищённые запросы разделены политикой skipReauth, поэтому 401 на форме входа — это ошибка ввода, а не повод запускать refresh-цикл.
5. Ответ на неудачный вход не раскрывает, что именно неверно — логин или пароль.
6. Валидация ввода через Zod до отправки запроса.
7. Нет XSS-синков. В коде отсутствуют dangerouslySetInnerHTML, eval и прямые присваивания innerHTML — весь пользовательский ввод рендерится через React, который экранирует его автоматически.
8. Централизованная очистка состояния при выходе через session listener — данные пользователя не остаются в кэше RTK Query.
9. Моки и тестовые учётные данные не попадают в прод-сборку: импорт mocks/browser динамический и стоит под import.meta.env.DEV, поэтому строка admin в собранном JS отсутствует.

### Что в текущей сборке фактически НЕ защищено

Это демо-проект без бэкенда, и реальных гарантий безопасности он не даёт:

- Cookie не HttpOnly. В handlers.ts выставляется access_token=access; path=/ — без флага HttpOnly. Более того, флаг там невозможен: обработчики сами читают cookie через document.cookie, а HttpOnly именно это и запрещает.
- Cookie не Secure. Ничто не запрещает передачу по HTTP; compose поднимает контейнер на http://localhost:8080 без TLS.
- Токен — константа. Значение токена в моках — литеральная строка 'access'. Ни подписи, ни срока жизни, ни привязки к пользователю.
- Сессия подделывается в одну строку. document.cookie = 'access_token=access' в консоли браузера даёт полный доступ.
- /api/refresh всегда возвращает 200. Обновление успешно при любых условиях, поэтому ветка dispatch(logout()) при неудачном refresh на моках практически недостижима.
- Учётные данные в бандле. admin / admin лежат в mocks/data/auth.ts и попадают в собранный JS (только в dev; в прод-сборке их нет).
- «Бэкенд» исполняется в браузере. В dev-режиме все проверки доступа выполняются на машине пользователя внутри MSW и снимаются отключением service worker'а.
- Профиль в localStorage. PUT /api/profile кладёт данные в localStorage открытым JSON под ключом mock_profile, без шифрования и без привязки к пользователю.
- Нет заголовков безопасности. В nginx.conf не заданы Content-Security-Policy, X-Frame-Options, X-Content-Type-Options, Referrer-Policy, HSTS.

### Что потребуется для реального продакшена

1. Заменить MSW на настоящий бэкенд на том же origin по пути /api.
2. Выдавать сессию сервером с флагами HttpOnly; Secure; SameSite=Lax, коротким TTL у access-токена и отдельным refresh-токеном, ограниченным путём /api/refresh.
3. Подписывать токены, проверять подпись и срок жизни на сервере, реализовать ротацию и отзыв refresh-токенов.
4. Перевести раздачу на HTTPS и добавить в nginx.conf CSP и сопутствующие заголовки.
5. Добавить на сервере rate limiting на /api/authorization и хранить пароли хешированными (bcrypt/argon2).

## Известные ограничения

1. Поле valueWhenDisabled в типе ProfileField объявлено, но не используется. Изначально планировалось, что при блокировке поля в него подставляется предустановленное значение («не применимо»). Сейчас disabledWhen только блокирует поле, значение не подставляется. Если нужно — доработка в одну строку в edit-view или в handleChange.

2. Профиль хранится в localStorage браузера. Данные не синхронизируются между устройствами и не переживают очистку хранилища. Это осознанное упрощение мока, в проде будет реальный бэкенд.

3. Моки на MSW работают только в dev-режиме. Docker-контейнер раздаёт статику, но без бэкенда приложение в нём не работает. Это ожидаемое поведение: контейнер демонстрирует сборку, а не полноценный деплой.

4. В dev-режиме React StrictMode монтирует компоненты дважды, поэтому /me на старте может уйти дважды. В прод-сборке этого нет.
