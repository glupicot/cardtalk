# CardTalk

SPA для изучения английских слов: карточки с переводом и примером употребления, фильтр по темам, профиль пользователя с большой формой и валидацией, сессионная авторизация на cookie.

Проект представляет собой фронтенд без реального бэкенда — весь API эмулируется через MSW (Mock Service Worker) прямо в браузере. Это важно для понимания раздела «Защищённость данных».

## Стек

- React 19 — UI
- TypeScript ~6.0 — типизация
- Vite 8 — сборка и dev-сервер
- Redux Toolkit + RTK Query 2.12 — стор, кэш и слой данных
- React Router 7 — маршрутизация
- React Hook Form + Zod 7.88 / 4.6 — формы и валидация
- MSW 2.15 — мок API через Service Worker
- CSS Modules — стили, изолированные по компонентам
- ESLint 10 — статический анализ

## Запуск

Вариант 1: npm (разработка)

Требования: Node.js 20.19+ или 22.12+ (ограничение Vite 8), npm 10+.

    npm install
    npm run dev

Приложение поднимется на http://localhost:5173.

При первом запуске MSW регистрирует service worker из public/mockServiceWorker.js. Если вы обновляли версию MSW, воркер нужно перегенерировать:

    npx msw init public/ --save

Вариант 2: Docker

Требования: Docker 20.10+ с плагином Compose.

    docker compose up -d --build

Приложение будет доступно на http://localhost:8080.

Как устроен образ

Сборка двухстадийная (Dockerfile):

1. Стадия build — node:20-alpine. Сначала копируются только package*.json и выполняется npm ci: это отдельный слой, который Docker переиспользует из кэша, пока не изменился package-lock.json. Затем копируется исходный код и выполняется npm run build → dist/.
2. Стадия рантайма — nginx:alpine. В неё переносится только готовый dist/, без node_modules и исходников. Итоговый образ содержит статику и nginx, Node.js в нём нет.

nginx.conf делает две вещи:

- try_files $uri $uri/ /index.html — SPA-фоллбэк. Без него прямой заход на /cards или перезагрузка страницы давали бы 404, потому что таких файлов на диске нет, а маршрутизация живёт на клиенте.
- gzip on с перечнем text/js/css/json типов — сжатие статики.

.dockerignore исключает node_modules, dist, .git и мусор IDE из контекста сборки.

MSW запускается только в dev-режиме (import.meta.env.DEV в main.tsx), поэтому в продакшен-сборку моки не попадают. Для работы контейнера с реальным API нужен бэкенд на том же origin по пути /api.

## Что реализовано

### Архитектура данных

Слой данных построен на RTK Query.

Признак авторизации — поле login в user-slice. Если оно непустое, пользователь считается авторизованным. Отдельного флага isAuth нет, чтобы не было двух источников правды.

Обработка 401 централизована в baseQueryWithReauth. Публичные ручки (login, logout) помечены флагом skipReauth и не запускают цикл обновления токена. Это важно: если неправильный пароль возвращает 401, попытка «обновить сессию» превратила бы сообщение «неверный пароль» в «сессия истекла».

Очистка состояния при выходе централизована в session listener (store/index.ts). Listener подписан на logout и на authApi.endpoints.logout.matchFulfilled. Компонент делает dispatch(logout()), а listener сбрасывает кэш RTK Query. Это работает даже если запрос /logout не дошёл: экшен logout всё равно диспатчится.

### Оптимизация загрузки

Все страницы подключены через React.lazy — index.ts рядом с каждой страницей объявляет ленивую обёртку. В app.tsx они обёрнуты в Suspense. В сборке это видно по отдельным чанкам: home-page, login-page, cards-page, profile-page, not-found-page грузятся по требованию, а не одним бандлом.

### Карточки

- GET /api/words через RTK Query, данные лежат в mocks/data/words.ts.
- Карточка переворачивается по клику: лицевая сторона — слово и часть речи, оборот — перевод.
- Список тем не захардкожен, а вычисляется из самих слов: useMemo собирает Set из всех word.topics. Добавление слова с новой темой автоматически добавляет фильтр.
- Фильтрация по выбранной теме тоже в useMemo, чтобы не пересчитывать список на каждый ререндер.
- Заголовки карточек берутся из constants/motivation-titles.ts.

### Профиль

Форма профиля описана декларативно: constants/sections.ts — это данные, а не разметка. Каждое поле задаётся объектом { name, label, type, value, ... }, сгруппированным по секциям («Личные данные», «Контакты», «Обучение», «Предпочтения»). Компонент field работает как диспетчер и по field.type рендерит нужный контрол.

Типы полей: text, number, textarea, date, select, checkbox (множественный выбор), radio. В types/profile.ts это оформлено дискриминированным объединением ProfileField с дискриминантом type. Благодаря этому TypeScript точно знает, что у CheckboxField поле value — это string[], а у NumberField — string, и перепутать их на этапе компиляции нельзя.

Форма управляется React Hook Form с валидацией через Zod (schemas/profile-schema.ts). EditView не рендерится, пока не пришли данные с сервера — иначе reset затирал бы то, что пользователь успел ввести.

Реализована связанность полей — два независимых механизма:

- visibleWhen: { field, value } — поле показывается только при определённом значении другого поля. Пример: «Имя супруга» появляется, только если семейное положение — «Женат/Замужем».
- disabledWhen: { field, value } плюс valueWhenDisabled — поле блокируется и получает предустановленное значение. Пример: «Девичья фамилия» при «Не женат/Не замужем» блокируется и заполняется значением «не применимо». При снятии условия поле очищается.

Зависимости вычисляются на каждом рендере через watch() — при изменении поля maritalStatus перерисовываются зависимые поля.

Сохранение — PUT /api/profile, результат показывается тост-уведомлением.

### Числовые поля

Field для type: 'number' рендерит input как type="text" с inputMode="numeric" и санитайзит значение регуляркой /\D/g. Это сознательный уход от нативного type="number": нативный инпут даёт ввести e, +, -, точку и в некоторых браузерах возвращает пустую строку при невалидном вводе, что ломает контролируемый компонент. Хранение значения как строки позволяет полю быть пустым, а не «залипать» на нуле.

### UI-компоненты

- Кастомный Select отрисовывается через createPortal вне DOM-потока родителя — так выпадающий список не обрезается overflow: hidden у контейнеров. Позиция вычисляется от кнопки, и при нехватке места снизу список раскрывается вверх (флип). Заблокированный селект не открывается по клику.
- Toast — уведомления об успехе и ошибке с автозакрытием.
- Header / Footer / Body — каркас страницы.
- Лейблы связаны с инпутами через htmlFor и id (для текстовых полей, textarea и date).
- Стили изолированы через CSS Modules, шрифты (Inter, Fraunces, Unbounded) лежат локально в assets/fonts и не тянутся со сторонних CDN.

### 404

Маршрут * показывает NotFoundPage — для любого URL, который не подошёл под остальные маршруты.

## Алгоритм авторизации

Авторизация построена по сессионной схеме на cookie с автоматическим обновлением по 401.

### 1. Вход

1. login-page использует React Hook Form с zodResolver(loginSchema). Схема (schemas/login-schema.ts) требует непустые логин и пароль; режим mode: 'onBlur' показывает ошибку при уходе с поля, а не на каждый символ.
2. Сабмит вызывает мутацию useLoginMutation → POST /api/authorization с телом { login, password }. Ручка помечена skipReauth: true, чтобы 401 от неправильного пароля не запускал refresh.
3. Обработчик в mocks/handlers.ts сравнивает пару с ADMIN_LOGIN / ADMIN_PASSWORD из mocks/data/auth.ts. Совпало — 200 { name: 'Admin' } и заголовок Set-Cookie: access_token=access; Path=/; SameSite=Lax. Не совпало — 401 { message: 'Invalid credentials' }.
4. При успехе клиент делает dispatch(setUser(response.name)) — в user-slice записывается имя, что равнозначно «пользователь авторизован». Дальше navigate(ROUTES.CARDS).
5. При ошибке .unwrap() бросает исключение, и в catch вызывается setError('password', ...) — под формой появляется «Неверный логин или пароль». Ответ сервера намеренно не различает «нет такого логина» и «неверный пароль», чтобы не давать подсказку для перебора учётных записей.

### 2. Транспорт запросов

store/slices/base-query.ts:

    export const baseQuery = fetchBaseQuery({
      baseUrl: '/api',
      credentials: 'include',
    });

credentials: 'include' заставляет браузер прикладывать cookie к каждому запросу автоматически. Токен нигде не хранится в JS-коде и не подставляется руками в заголовок Authorization — приложение вообще не оперирует значением токена, им управляет браузер.

### 3. Восстановление сессии

Отдельного запроса /me при загрузке приложения нет. Восстановление сессии происходит по факту первого защищённого запроса. Если пользователь открывает /cards, useGetWordsQuery дёргает /words. Если cookie живая — 200, данные подтягиваются. Если нет — 401, дальше логика reauth либо обновляет токен, либо разлогинивает. Такой подход убирает лишний запрос для гостя и не даёт циклов «запрос → 401 → refresh → 401 → logout → запрос».

### 4. Автообновление токена при 401

Обёртка baseQueryWithReauth, через которую проходят все запросы, кроме помеченных skipReauth:

    запрос → 401? — нет → ответ
              │
             да
              ▼
       POST /api/refresh
              │
       ┌──────┴──────┐
    успех          провал
       │              │
  повтор запроса   dispatch(logout())

Ключевая деталь — дедупликация refresh-запросов. Если страница одновременно запрашивает /words и /profile, и оба получают 401, наивная реализация отправила бы два параллельных /refresh. Здесь промис обновления хранится в переменной модуля refreshRequest:

    if (refreshRequest) return refreshRequest;

Первый упавший запрос инициирует обновление, остальные получают тот же самый промис и ждут его. После завершения .finally() обнуляет переменную, чтобы следующий цикл 401 мог запустить новый refresh. Это классический паттерн single-flight.

Если refresh прошёл — исходный запрос повторяется прозрачно для вызвавшего компонента. Если не прошёл — диспатчится logout(), и приложение переходит в неавторизованное состояние.

### 5. Выход

Мутация logout → POST /api/logout. Обработчик отдаёт Set-Cookie: access_token=; Path=/; Max-Age=0, что удаляет cookie. Дальше Header диспатчит logout() из user-slice, session listener в store/index.ts ловит экшен и сбрасывает кэш RTK Query. Пользователь редиректится на главную.

### 6. Ограничение доступа к страницам

Проверка сделана на уровне страниц:

- cards-page и profile-page смотрят на login из user-slice. Если пусто — Navigate to /.
- Публичные страницы (главная, логин, 404) доступны всем.

## Защищённость данных

Здесь нужно чётко разделить два уровня: какая схема заложена в архитектуру клиента и что реально защищено в текущей сборке.

### Что сделано правильно с точки зрения схемы

Клиент написан под корректную серверную модель безопасности:

1. Токен не хранится в localStorage и не проходит через JS. Токен в localStorage читается любым исполнившимся на странице скриптом — то есть одна XSS-уязвимость или одна скомпрометированная npm-зависимость означает угон сессии. Здесь сессия передаётся через cookie, которую браузер прикладывает сам (credentials: 'include'), и код приложения значение токена не видит и не трогает.
2. SameSite=Lax на cookie — базовая защита от CSRF: браузер не приложит cookie к межсайтовым POST-запросам, инициированным сторонним сайтом.
3. Авторизация проверяется на стороне «сервера». Каждый защищённый обработчик (/profile, /words) самостоятельно проверяет сессию и отдаёт 401. Клиентские проверки отвечают только за UX — за то, чтобы не показывать пустые экраны, — но не являются механизмом контроля доступа.
4. Централизованная обработка 401. Ни один компонент не работает с сессией сам — вся логика в одном baseQueryWithReauth.
5. Публичные ручки помечены skipReauth. 401 на форме входа — это ошибка ввода, а не повод запускать refresh-цикл.
6. Ответ на неудачный вход не раскрывает, что именно неверно — логин или пароль.
7. Валидация ввода через Zod до отправки запроса.
8. Нет XSS-синков. В коде отсутствуют dangerouslySetInnerHTML, eval и прямые присваивания innerHTML — весь пользовательский ввод рендерится через React, который экранирует его автоматически.
9. Централизованная очистка состояния при выходе через session listener — данные пользователя не остаются в кэше RTK Query.

### Что в текущей сборке фактически НЕ защищено

Это демо-проект без бэкенда, и реальных гарантий безопасности он не даёт:

- Cookie не HttpOnly. В handlers.ts выставляется access_token=access; Path=/; SameSite=Lax — без флага HttpOnly. Более того, флаг там невозможен: обработчики читают cookie через document.cookie, а HttpOnly именно это и запрещает.
- Cookie не Secure. Ничто не запрещает передачу по HTTP. Compose поднимает контейнер на http://localhost:8080 без TLS.
- Токен — константа. Значение токена — литеральная строка 'access'. Ни подписи, ни срока жизни, ни привязки к пользователю.
- Сессия подделывается в одну строку. document.cookie = 'access_token=access' в консоли браузера даёт полный доступ.
- /api/refresh всегда возвращает 200. Обновление успешно при любых условиях, поэтому ветка dispatch(logout()) при неудачном refresh на моках практически недостижима и не покрыта проверкой.
- Учётные данные в бандле. admin / admin лежат в mocks/data/auth.ts и попадают в собранный JS.
- «Бэкенд» исполняется в браузере. В dev-режиме все проверки доступа выполняются на машине пользователя внутри MSW и снимаются отключением service worker'а.
- Профиль в localStorage. PUT /api/profile кладёт данные в localStorage открытым JSON под ключом mock_profile, без шифрования и без привязки к пользователю.
- Нет заголовков безопасности. В nginx.conf не заданы Content-Security-Policy, X-Frame-Options, X-Content-Type-Options, Referrer-Policy, HSTS.

### Что потребуется для реального продакшена

1. Заменить MSW на настоящий бэкенд. Сейчас моки исключены из прод-сборки (main.tsx стартует воркер только при import.meta.env.DEV), но в проде нужен реальный сервер на том же origin.
2. Выдавать сессию сервером с флагами HttpOnly; Secure; SameSite=Lax, коротким TTL у access-токена и отдельным refresh-токеном, ограниченным путём /api/refresh.
3. Подписывать токены, проверять подпись и срок жизни на сервере, реализовать ротацию и отзыв refresh-токенов.
4. Перевести раздачу на HTTPS и добавить в nginx.conf CSP и сопутствующие заголовки.
5. Добавить на сервере rate limiting на /api/authorization и хранить пароли хешированными (bcrypt/argon2).
